## 4. 数据截点测试

**做法**（`pilot/cutoff_invariance.py`）：在项目外的临时目录建两棵替代原始数据树，只含冒烟的 100 只股票、3 个指数、日历、上市表、东财 / 新浪分红与新浪配股表、截点之前的全部 Z_O 文件。
- **树 A（删除）**：每个按股票的表用装载器自己的截点规则切到 2021-12-31（日线、指数、日历：日期 ≤ 截点；事件：除权日 ≤ 截点，或无除权日且公告日 ≤ 截点，行内晚于截点的日期置空）；截点之后的 Z_O 月度 / 年度文件不放进去；上市表中晚于截点的上市 / 退市日期置空。
- **树 B（乱填）**：树 A 加上截点之后的合成数据——每只股票的日线追加 2022-01-03 至 2026-06-30 每个工作日一行随机价量与状态（共 114,338 行），指数同样追加随机行，日历追加带随机交易日标志的日子，每张事件表追加 3 行除权日在 2022–2026 年的随机行，上市表给约 30% 的在市股票随机填一个 2022–2026 年的退市日，截点之后的 Z_O 文件共 167 个：一半写成**不是 parquet 的字节**（只要被打开就会报错），一半写成内容随机的合法表。
- **两棵树都是在不读取任何截点之后数据的情况下构造的**：树 A 只经截点读取器写出，树 B 只追加生成的数据。

**结果**（`experiments/results/pilot/cutoff_test/cutoff_invariance.json`）：用同一配置、同一份股票名单，在真实数据树、树 A、树 B 上各跑一次完整的冒烟管线。

|---|---|
| `results.json`（去掉阶段耗时、回测耗时、输出路径后的 SHA-256） | 三次**逐位相同** |
| `standard_orders.parquet`（内容哈希） | 三次**逐位相同** |
| 特征面板文件 | 97 / 97 三次**逐位相同** |

**过程中发现并修正的一处问题（如实记录）：** 第二次截点测试时（`cutoff_invariance_run2.json`），标准订单与 97 个特征文件已经逐位相同，但三次运行的 `results.json` 在 VT 一种方法的"净交易额 ‖trade_t‖₁"及由它算出的订单层恒等式残差上有末位差异（共 9 处，全部是这两个量）。原因不是数据泄漏，而是引擎账本按 `set` 的迭代顺序对交易向量求和，Python 的字符串哈希在每个进程里随机，浮点求和顺序因此因进程而异。修正（引擎 `ledger.end_day`、`attribution.reference_cost` 一律按排序后的代码迭代）后重跑引擎全部测试 118 / 118（残差与修正前逐位相同），再做第三次截点测试，三次运行完全一致。这同时说明：**同一配置的重复运行现在逐位可复现**。另：第一次截点测试的两次运行（旧代码）因为我在它们运行期间修改了试点代码（之后启动的工作进程载入了新代码，与主进程不一致），树 A 一次在估计阶段报错；树 B 第一次启动即失败（没有留下输出，原因未查明），重跑后同样在估计阶段报错。这两次结果作废，未用于任何结论。
