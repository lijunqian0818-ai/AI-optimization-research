## 1. 实现了什么

| 文件 | 内容 |

| `simulate.py` | 日循环：把预先给定的提名清单变成订单、合成成交与记账（H+1 个资金袖套、数量按涨停价预定、买单未成交即撤、卖单逐日重挂）。不含任何模型或信号 |

### 2.3 独立对账（随机合成市场）

设置：5 个种子（11、23、37、41、53），面板起始日分别为 2012-10-08、2015-06-01、2020-06-01、2023-06-01、2017-03-01（前四个各跨一个规则变更日），每个面板 150 个交易日、24 只证券，含停牌、涨跌停开盘、无成交日、缺行、缺收盘价、派息、送转、缩股、配股、现金退出、承继、U 类事件、退市。两个策略 G、B 在同一市场上交错入场 / 持有 / 退出。测试用 H = 3、K = 6（测试配置，不是方案的 H = 5、K = 30）。每个种子 380–617 个批次。

5 个种子的最大残差（除注明外均相对 W0 = 1e7）：

| 检查 | 最大残差 |
|---|---|
| 朴素实现（逐批次现金流累加）的期末财富 vs 台账 | 1.8e-15 |
| R2：收益法轨道 vs 股数台账，逐日（相对 W_{t−1}） | 6.0e-16 |
| R2：累计 | 7.2e-16 |
| R1：Lemma 3 残差（元口径） | 1.4e-16 |
| R1：另一种排序 | 9.3e-17 |
| 归因三项之和 vs 两策略财富变动之差 | 8.1e-16 |
| R1：财富归一化口径（绝对值） | 2.8e-17 |
| 归一化三项之和 vs 两策略日收益之差的累计（绝对值） | 1.4e-15 |
| 股数向量交易额 vs 成交记录 | 2.8e-17 |
| 非零现金收益下的递推 Π + Σρ_t(W_t − c_t) | 5.6e-16 |

- 作为对照，把递推写成 Π + Σρ_t·W_t（期末扣费的公式）时，差距为 0.9e-6 至 1.7e-6，比正确公式的残差大约九个数量级，说明这项检查分得开两种公式。
- 买单成交判定用整数运算独立重推，每个种子 1,149–1,195 笔，不一致 0 笔。
- 没有订单的策略-日（G、B 两个策略合计，每个种子 10–17 个）上，交易额与成本恰为 0。

**这套对账的独立性有限，需要说明：**
- 朴素实现与引擎共用行情容器和规则日历的费率查询（后者单独用手写期望值测过），成交清单（入场日、证券、股数、卖出日）取自台账的运行结果。成本、公司行为、核销、期末估值（含 P1 / P1-R）是另写的。
- 买单重推只覆盖 SF 的买入，不覆盖卖出，也不覆盖 SF-strict / SF-loose。
- Lemma 3 是代数恒等式，残差接近机器精度是预期之中的；有信息量的是前两行和"三项之和 vs 财富差"。
- 覆盖不均：承继（S-e）在随机测试里只有 1 个种子的 1 个批次碰到，现金退出只在 2 个种子出现；"全天无订单且持仓有公司行为"五个种子合计只有 1 天。这些路径主要靠 §2.2 的手算用例。

### 2.4 首轮运行中的失败及处理

测试首轮有 3 处失败，都是我写的期望有误，不是为了通过而改期望：

1. 我断言 Python 内置 `round` 在 10.05、10.15 两个例子上会算错，实际没有。这是关于 Python 的断言，不是引擎的期望值；删掉后改成了 §2.1 的全网格整数比对。
2. "停牌 30 天后复牌当日卖出成交"的期望漏掉了容量上限：复牌当日的 20 日均额为 0，上限为 0，卖单按 PLAN 的写法不成交，次日才成交。引擎行为与 PLAN 文字一致，期望改为"复牌日 S3、次日成交"，并加了一条断言：不设上限（SF-loose）时复牌日成交。这同时是 PLAN 的一个缺口，见 §4 第 5 条。
3. 两策略用例里，我给 G 安排的第二个批次恰在窗口最后一天到期卖出，导致"G 期末有未平仓"不成立。这是场景构造错误，把买入日后移一天。

## 9.6 确定性修正（试点的截点测试发现；2026-11-16）

试点的截点不变性测试（`experiments/results/pilot/PILOT_SMOKE_REPORT.md` §4）第二次运行时，三次运行的结果只在 VT 的"净交易额 ‖trade_t‖₁"及由它算出的订单层恒等式残差上有末位差异，其余全部逐位相同。原因：`Ledger.end_day` 按 `set(pre) | set(post)` 的迭代顺序建交易向量，`net_traded_amount` 对它求和；Python 的字符串哈希在每个进程里随机化，集合的迭代顺序因而因进程而异，浮点求和的顺序跟着变。**修正**：`ledger.end_day` 的 `r["ov"]` 与 `r["trade"]`、`attribution.reference_cost` 的成交循环一律按排序后的代码迭代。不改变任何记账规则，只固定求和顺序。修正后 `run_all.py` 重跑 118 / 118 通过，§9.1 的各项残差与修正前逐位相同；约定文件哈希不变（改的不是 `config.py` / `rule_calendar.py`）。
